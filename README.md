# Недельный отчет RECTOP

Веб-панель для недельного отчета: дашборды показывают месяцы, недели, графики и события, а вкладка `Админка` нужна для ежедневного ввода факта.

## Что есть

- `Все месяцы`: длинная недельная лента всех месяцев.
- `Обзор месяца`: KPI, выполнение плана, воронка, конверсии и недельные графики месяца.
- `Неделя`: детальный ввод/просмотр выбранной недели.
- `Админка`: ежедневный ввод `МСК / СПБ / Сообщения` x `Лиды / КВАЛ / Продажи`.
- `Сообщения`: отдельная витрина, не смешивается с городами.
- `Переход → лид`: визиты и лиды Roistat за один период, конверсия по источникам, брендам и их сочетаниям.
- `Спрос`: Wordstat по запросу «автошкола» для Москвы и СПб; фиксированные месяцы январь–декабрь и отдельная линия для каждого года.
- `События`: календарь внешних и внутренних факторов.

## Логика данных

- `Все` = `МСК + СПБ`, без сообщений.
- `МСК` = только Москва.
- `СПБ` = только Санкт-Петербург.
- `Сообщения` считаются отдельно.
- Новый месяц создается с планами по `МСК`, `СПБ`, `Сообщениям` и трем метрикам.
- Дневные планы распределяются автоматически по датам месяца.

## Google Sheets

### Переход → лид

Отдельный срез Roistat сохраняется в `Lead_Conversion_Daily`. Запрос `analytics/data` использует дневной интервал, измерения `host`, `marker_level_1`, `utm_campaign` и `utm_medium`, показатели `visits` и `leads` и московские границы дат. Конверсия — сумма лидов / сумма визитов × 100%; при нулевом знаменателе выводится прочерк. Это визиты сайта, а не рекламные клики или уникальные посетители. Используется исходная атрибуция Roistat, без перераспределения мессенджеров и нераспознанного и без смешивания с amoCRM, ПС, Метрикой и старыми недельными данными брендов.

Школы и города определяются по снимку [справочника UTM](https://docs.google.com/spreadsheets/d/1HPrDFKrgJqUPIbX_VkFQzJbEIayUYMAFsRIzThaEYS4/edit#gid=0) от 28.10.2026, сохранённому в `apps-script/SchoolRegistry.gs`: точный `utm_campaign`, город `msk/spb` из `utm_medium`, затем полное совпадение домена с меткой школы. Отдельные строки и фильтры сохраняют город школы: АвтоДрайв МСК и СПб, ИзиДрайв МСК и СПб и прочие. У общих доменов без однозначных UTM город остаётся «Не определён»; конфликтующие привязки не назначаются принудительно. Пустые города справочника не заполняются по расположению строки. Снимок справочника обновляется в коде явно, исходная таблица не изменяется. Старые десятиколоночные кэши читаются без миграции и обогащаются справочником; новая загрузка сохраняет UTM и enum ID школы.

Источники сгруппированы в Яндекс Карты, Гугл Карты, 2ГИС, Директ, Сайт, Справочники, Нейросети, Прямые визиты, ВКонтакте, Мессенджеры и прочие каналы. По подтверждённым правилам пользователя «Сайт» включает `yandex`, SEO/organic и переходы с сайтов; «Справочники» — `yell.ru`, `spravker`; «Нейросети» — `perplexity`, `chatgpt.com`. Эти правила применяются и к исходным кодам с префиксом `:utm:`. Проектные коды `ya/go` взяты из листа «Источники» справочника, `geoadv_*maps*` и `geoadv_search_organization_list` относятся к карточкам Яндекса. Native ID `direct8/direct9` определяют Директ даже при брендовой подписи, а прямые визиты остаются отдельной группой. Неоднозначные коды остаются в «Прочие / Нераспознанное». Исходные подписи и коды сохранены и доступны под строкой канала. Конверсия группы всегда пересчитывается по сумме лидов и переходов.

`getLeadConversion` читает сохранённый срез выбранного месяца. Кнопка «Обновить» вызывает защищённое действие `syncLeadConversion` с первого числа выбранного месяца до сегодняшнего дня (или конца прошлого месяца). Покрытие означает успешно запрошенный период, а не последнюю дату с визитами. Ошибка провайдера сохраняет прежний кэш. Ключ и проект используются из существующих Script Properties; новых подключений не требуется. Формат запроса описан в [документации Roistat](https://help-en.roistat.com/API/methods/analytics/).

Дополнительно по уточнению пользователя `autoschool-firmika.ru`, `jsprav` и `jsprav.ru` относятся к «Справочникам», `ig` — к отдельной группе «Инстаграм», а `2dqc` считается опечаткой `2gis` и относится к «2ГИС». Префиксы `utm:`, `:utm:` и одиночное двоеточие перед меткой нормализуются только для классификации; исходные метки остаются в деталях.

В интерфейсе «Переход → лид» показаны только пять каналов: Яндекс Карты, 2ГИС, Гугл Карты, Сайт и Директ. Фильтр применяется до подсчёта KPI, брендов, вложенной детализации, графика и блока «Без города», поэтому итог бренда равен сумме его показанных источников. По кнопке в строке бренда раскрывается вложенная таблица с переходами, лидами и CR каждого источника; МСК и СПб остаются отдельными школами. Другие источники сохранены в исходном кэше и классификаторе, но скрыты из этого интерфейса.

### Wordstat

Вкладка «Спрос» читает лист «История спроса» [готовой выгрузки Wordstat](https://docs.google.com/spreadsheets/d/1lBIgNVVyg7fT7j_rjVybfxUMBZ74NiuWDfPm3BZsIAY/edit#gid=18600011): Москва и СПб, широкая частотность «автошкола», история с 2018 года. Каждый год — отдельная линия, месяцы фиксированы. Листы с последними 30 днями в сезонность не включены. Чтение не вызывает API Яндекса; «Обновить из таблицы» сохраняет проверенную историю в `Wordstat_Demand`. При ошибке доступен только кэш того же источника. Прямой API включается отдельно свойством `WORDSTAT_SOURCE_TYPE=api`; его ключ и ID каталога остаются в Script Properties. История не дополняется вымышленными нулями. Обновление исходной таблицы выполняет её меню Wordstat; в чате настроен запуск по понедельникам в 10:00 МСК. Подробности: [WORDSTAT_SETUP.md](WORDSTAT_SETUP.md).

Apps Script создает и использует служебные листы:

- `Month_Config`
- `Month_Plans`
- `Data_Daily`
- `Weekly_Summary`
- `Event_Map`

Действия моста:

- `verifyPassword`
- `getMonths`
- `getMonthData`
- `createMonth`
- `upsertDailyValues`
- `upsertEvent`

## Подключение

1. Открыть Google Sheets.
2. Открыть Apps Script.
3. Вставить код из `apps-script/AppsScript.gs`.
4. Запустить `setupWeeklyReportService`.
5. Запустить `setWeeklyReportPassword("ваш-пароль")`.
6. Опубликовать Apps Script как Web App.
7. Добавить URL в переменные окружения:

```text
VITE_APPS_SCRIPT_URL=https://script.google.com/macros/s/.../exec
VITE_ADMIN_PASSWORD=ваш-пароль
```

Для GitHub Pages добавьте `VITE_APPS_SCRIPT_URL` в GitHub: Settings -> Secrets and variables -> Actions -> Variables или Secrets. Пароль админки в GitHub Pages не добавляйте: его нужно вводить в панели, иначе он попадет в публичный JS.

Если `VITE_APPS_SCRIPT_URL` не задан, панель работает в локальном fallback на демо-данных.

## Проверка перед публикацией

### Импорт источников Roistat

Кнопка `Roistat: источники` запрашивает API за выбранный период с дневными интервалами `interval: '1d'` и сохраняет результат в `Data_Daily`. Даты берутся из `dateFrom` каждого интервала. Это один запрос вместо запроса на каждый день; временные ошибки 429/5xx повторяются с теми же полями. Токен хранится только в Script Properties (`ROISTAT_API_KEY`), номер проекта — в `ROISTAT_PROJECT_ID`. Используются воронки `МСК АШ` и `СПБ АШ`; сообщения остаются отдельным отчетом. Формат запроса: [официальная документация Roistat](https://help-en.roistat.com/API/methods/analytics/).

Нераспознанное, другие источники и мессенджеры распределяются расчетно по всем распознанным источникам, включая Директ и Рек/кешбэк. Вес — исходное значение того же показателя за выбранный период в каждом месяце и городе: отдельно лиды, КВАЛ, продажи, выручка и расходы. Сначала методом наибольшего остатка фиксируется целочисленная доля каждого источника на весь период, затем эти доли распределяются по дням с сохранением дневных итогов. Так меняющийся объем нераспознанного не искажает месячные пропорции. Если базы нет во всем периоде, импорт сообщает об ошибке до изменения сохраненных данных.

Повторный импорт заменяет прежние строки Roistat за период (API, spreadsheet и report-24), сохраняя ручные данные. Маркер `[SOURCE_ATTRIBUTION=proportional-v1]` защищает импорт от повторного пересчета на экране и замены Директа помесячной таблицей. Это расчетная атрибуция, а не установленные источники отдельных заявок.

Строки источников записываются пакетами через `setValues`, а прежние импорты удаляются смежными диапазонами. Это сокращает число обращений к Google Sheets и позволяет импортировать месяцы в пределах времени выполнения Apps Script.

### Расходы по источникам

Месячные бюджеты загружаются из таблицы [ДРР](https://docs.google.com/spreadsheets/d/1tl-e_HAxxgGv24l19GaKaVz_6NYDuLqEwQH5esjER3o/edit) независимо от долгой загрузки аналитики брендов. Для сентября 2026 используются листы `МСК СЕНТЯБРЬ 26` и `СПБ СЕНТЯБРЬ 26`: столбцы E — Яндекс Карты, I — 2ГИС, K/L — название и бюджет другого источника, M — общий бюджет. Авито и реклама в метро сохраняются отдельно; остаток общего бюджета виден как «Прочие расходы». Итоги без названия бренда повторно не учитываются.

ДРР имеет приоритет над расходами Roistat и старыми данными брендов для того же месяца. В отчёте суммы обозначены как месячные бюджеты, без распределения по дням. В месяце без ДРР используются имеющиеся расходы Roistat или аналитики брендов. Если их тоже нет, выводится прочерк; условные 50 000 ₽ для SEO и Google больше не подставляются. В составном периоде известная часть помечается `*`, финансовые коэффициенты с неполным расходом не рассчитываются. На 15.10.2026 листов за октябрь 2026 в ДРР нет.

### Загрузка отдела продаж

Сервер читает `AmoCRM_Raw_Leads` один раз на запрос отчёта и использует тот же набор сделок для команды Дакоро и всего отдела. Соседние скалярные столбцы загружаются общими диапазонами, без `contactIds`, `customFieldsJson` и `rawJson`. При текущем порядке столбцов это два чтения вместо 66. Такой порядок устраняет тайм-аут интерфейса в 90 секунд на большом массиве сделок и сохраняет правила расчёта показателей.

### Обновление квалов в «Месяц по дням»

Кнопка «Обновить отчёт» импортирует лиды и квалы из amoCRM за весь выбранный месяц до сегодняшнего дня и продажи из ПС. Так изменения квалификации учитываются и у заявок, созданных раньше. После успешного импорта основной отчёт сразу перечитывает `Data_Daily`. В заголовке отдельно показаны дата лидов/квалов и покрытие продаж ПС. Рекомендации, прогнозы и планы сохраняются; рекомендации не вычитаются из общего числа заказов ПС.

Обновление существующих строк записывается смежными диапазонами, новые строки добавляются одним пакетом. Неполная выгрузка amoCRM или отсутствие нужных воронок прерывают импорт до замены фактов; ошибка возвращается в интерфейс.

### КВАЛ ОП, ОМ КВАЛ и источники продаж

Квалификация следует формуле столбца «Целевые лиды (технический)» листа «Выгрузка amoCRM» в отчёте «Новая Динамика», с отдельными правилами ОМ КВАЛ ниже. Пустой этап и этапы «Неразобранное», «Звонки», «Недозвоны», «На проверку», «В работе», «ЯГ ЛИДЫ», «Обзвон», «Отложенный спрос», «Иностранные права» не дают КВАЛ. Остальные открытые этапы и «Успешно реализовано» дают КВАЛ. Для «Закрыто и не реализовано» подходят причины: «Передумал учиться», «Выбрали другую школу», «Практика», «Дорого», «Хотят именно офлайн класс», «Не выходит на связь ЦЕЛЕВОЙ», а «Дубль ЦЕЛЕВОЙ» учитывается только в ОМ КВАЛ. Нецелевые дубли и другие причины закрытия исключены. Поле «Квал Лид = Да» и сохранённый ранее флаг не переопределяют это правило.

Целевой лид с текущим штатным ответственным amoCRM «Технический» или «Системный» относится к ОМ КВАЛ и исключается из КВАЛ ОП. Пользовательское поле менеджера не заменяет штатного ответственного при этом разделении. Основной отчёт сохраняет обе части отдельно; режим маркетинга складывает их. «Отдел продаж» считает КВАЛ ОП по тому же правилу.

Закрытые отказы с причиной `23760226` («Дубль ЦЕЛЕВОЙ») относятся только к ОМ КВАЛ при любом ответственном. У штатного РОП `10304986` только к ОМ КВАЛ относятся закрытые отказы с причинами `13957954`, `19999678`, `3421768`, `3421771`, `3421777` — точный набор из подтверждённого фильтра amoCRM. Остальные этапы РОП сохраняют общее правило квалификации; его успешные продажи считаются полностью. Для старых записей без ID причины допускается точное совпадение её названия.

Лиды и КВАЛ относятся к дате создания: пользовательское поле «Дата создания», затем штатная дата amoCRM по московскому времени. Текущий этап определяет квалификацию: созданный 30 сентября и квалифицированный 5 октября лид учитывается за 30 сентября. Правило одинаково для КВАЛ ОП и ОМ КВАЛ.

Продажи основного отчёта следуют «Динамике»: лист «Выгрузка PS» из той же таблицы, дата создания заказа, Москва/СПб, каждый заказ — одна продажа, A+B — две. Наличие договора, оплата, ответственный и поле «Кол-во» не ограничивают расчёт. Столбцы определяются по заголовкам; читаются только ID заказа, город, дата создания и A+B. Кнопка проверяет ПС до замены фактов; ошибки источника не подменяются продажами amoCRM. Отдельное защищённое действие `syncPsSales` обновляет только продажи. Обычное обновление выполняется с первого числа выбранного месяца; после частичных служебных обновлений для согласованного покрытия нужно обновить весь месяц.

Внутри покрытия нулевые дни считаются подтверждёнными. После последней даты выгрузки до конца месяца продажи помечаются `[PS_PENDING=1]`: интерфейс показывает пропуск и не включает день в среднее для прогноза. На 26.10.2026 ПС содержит 1–25 октября: 461 заказ + 23 A+B = 484 продажи, Москва 342 / СПб 142. Сентября в текущей выгрузке ПС нет, поэтому его сохранённые продажи остаются без изменения.

«Отдел продаж» сохраняет продажи amoCRM: текущий статус 142 в городских воронках, штатное `closed_at` по московским календарным дням, все типы и ответственные, A+B = 2. Выгрузка amoCRM сохраняет этот результат отдельно как диагностическую сверку и больше не перезаписывает продажи основного отчёта. «Источники» и «Бренды» используют Roistat.

В сравнительной «Динамике» договоры берутся из PS, а итог КВАЛ суммирует выбранные столбцы ответственных; совпадение квалификации отдельных сделок не гарантирует совпадение этих общих итогов. Вкладка «Источники» использует отдельный показатель QL из Roistat.
